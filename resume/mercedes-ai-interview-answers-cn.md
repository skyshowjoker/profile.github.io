## 二、AI Agent 与 LLM 应用

### 7. 请画出小艺智能体从用户输入到最终结果生成的完整架构。

主链路可以分为七层：入口与会话层接收用户请求；安全与权限层处理身份、内容安全和能力授权；路由与意图层识别任务类型；规划层把目标拆成依赖图；编排层调度主 Agent、Subagent 和工具；状态层保存会话、任务、步骤与产物；结果层进行校验、汇总并输出报告、PPT、卡片或文件。横向能力包括模型网关、Prompt/Skill 配置、日志指标、链路追踪、审计和灰度发布。

### 8. 多智能体调度引擎中，任务如何拆解、分配和执行？

首先把用户目标转换为结构化任务，包括目标、输入、输出、依赖、权限、超时和完成条件；再形成 DAG 或动态任务树。调度器根据依赖状态和 Agent 能力注册表选择执行者，将无依赖任务并行派发；执行结果写入任务状态和共享产物区，后续节点只读取经过校验的结果。任务失败时按错误类型决定重试、降级、重新规划或请求人工确认。
如何启动管理台
核心依据是数据依赖和副作用。若 B 必须使用 A 的输出，就顺序执行；若任务相互独立且资源允许，就并行执行；如果多个任务会写同一资源，即使数据上独立，也需要锁、版本或串行化。还要考虑模型并发额度、工具限流、成本和汇总复杂度。实践中可以把任务建模为 DAG，通过入度为零的节点集合决定当前可并行任务。

### 10. Agent 如何保存短期状态、长期状态和任务执行进度？

短期状态保存当前会话、最近消息和中间推理所需的结构化摘要；长期状态保存经过用户授权、可复用的偏好或知识，并设置过期和删除机制；任务进度以任务 ID、步骤 ID、状态机、输入输出哈希和检查点持久化。大文本和文件放对象存储，只在状态库保存引用。敏感内容需要加密、访问控制和保留期限。

### 11. 长时任务中断后如何接续？如何保证不重复调用工具？

每个步骤必须有持久化状态和幂等键。调用工具前记录 `PENDING/RUNNING`，成功后持久化结果、输出哈希和外部事务编号，再推进状态。恢复时从最近成功检查点开始，先查询外部操作是否已经完成，而不是直接重放。对于天然非幂等操作，采用业务唯一键、去重表、事务外盒或人工确认。

### 12. MCP 和普通 REST API、函数调用有什么区别？

REST 是通用服务通信风格；模型函数调用描述模型如何选择一个预定义函数；MCP 进一步标准化了 AI 应用发现和访问工具、资源与提示模板的方式，降低不同模型客户端和能力提供方的耦合。MCP 并不替代底层 REST，很多 MCP Server 内部仍调用 REST。它的价值主要在统一能力描述、会话交互和生态接入。

### 13. A2A 主要解决什么问题？与 MCP 如何配合？

A2A 关注 Agent 与 Agent 之间的能力发现、任务委派、状态交换和结果协作；MCP 更关注 Agent 如何访问工具和资源。一个典型流程是主 Agent 通过 A2A 把调研任务交给研究 Agent，研究 Agent 再通过 MCP 调用搜索、数据库和文档工具，最后通过 A2A 返回结构化结果。

### 14. Subagent 上下文如何与主 Agent 隔离？结果如何汇总？

主 Agent 只向 Subagent 传递完成任务所需的最小上下文、权限和输出 Schema，而不是复制整个会话。每个 Subagent 使用独立上下文窗口、工具白名单和资源预算。结果通过统一结构返回，包括结论、证据、置信度、错误和产物引用；主 Agent 再做去重、冲突检查和最终整合。

### 15. 多个 Agent 同时修改同一份文件或数据，如何处理冲突？

优先避免共享写入，把任务拆成独立产物后由单一汇总节点合并。如果必须并发修改，可采用版本号和乐观锁、字段级所有权、临时分支或补丁合并。提交时检查基线版本，冲突则重新读取、自动合并或交给人工确认。数据库写入还需事务和唯一约束兜底。

### 16. 什么情况下不应该使用多智能体架构？

任务简单、流程固定、延迟敏感、成本严格或需要强确定性时，单 Agent、规则引擎甚至普通服务更合适。多智能体会增加上下文传递、错误传播、调试和评测复杂度。只有当任务可以自然拆分、需要不同能力或并行执行收益明显时，才值得使用。

### 17. 92%+ 意图准确率如何定义？

我会先说明这是关键业务场景测试集上的分类准确率，而不是所有开放输入的总体正确率。定义为预测意图与人工标注一致的样本数除以总样本数，并同时看每类 Precision、Recall 和混淆矩阵，避免大类掩盖小类。实际回答要补充 `[样本数量、意图类别数、基线准确率]`。

### 18. 测试集如何构建？如何处理类别不平衡和污染？

从脱敏真实请求、产品标准用例和边界对抗用例中抽样，由至少两名标注者独立标注并解决分歧。按用户或时间切分训练、验证和测试集，防止同源表达泄漏。对小类采用分层采样，并报告宏平均 F1。Prompt 优化期间不能反复查看最终测试集，应保留冻结集做最终验收。

### 19. Prompt 优化前后的具体差异是什么？

优化通常包括明确角色和范围、提供意图定义与反例、规定决策顺序、要求结构化输出、加入置信度和澄清策略，并把易混淆类别的差异写清楚。评测时固定模型和参数，对同一数据集比较准确率、F1、格式成功率、Token 和延迟，避免只展示挑选案例。

### 20. 如何区分 Prompt、模型能力和业务规则问题？

先做最小复现。若补充明确指令或示例后稳定修复，多半是 Prompt 问题；若多种 Prompt 下仍无法完成推理或知识任务，可能是模型能力问题；若不同业务人员给出的正确答案不一致，则是业务定义或规则问题。还可以用强模型作为上界、规则基线作为下界做对照实验。

### 21. 如何防御 Prompt Injection？

把外部内容视为数据而非指令；系统指令与检索内容分层封装；对工具使用白名单、参数校验和最小权限；敏感操作增加策略引擎和人工审批；输出前做数据泄露和危险动作检查。对于网页或文档中的间接注入，要标记来源并禁止其覆盖系统策略。日志中记录触发规则，但不暴露系统提示词。

### 22. 用户意图模糊或包含多个目标时如何处理？

先判断是否存在完成任务所必需的缺失信息。缺失且猜测风险高时，提出一个最关键的澄清问题；可以安全默认时，明确假设后继续。多目标请求拆成子任务并展示计划，对有冲突的目标请求用户排序。高风险操作即使意图看似明确，也需要二次确认。

### 23. 如何控制大模型结构化输出，避免 JSON 解析失败？

优先使用模型原生结构化输出或 JSON Schema；限制字段和枚举；服务端使用严格解析和业务校验；失败时把错误信息用于有限次数的修复重试，而不是无限重新生成。关键业务不能只依赖 Prompt，必须在代码层验证类型、范围、必填字段和跨字段约束。

### 24. 工具调用失败时有哪些重试、降级和补偿机制？

先区分瞬时错误、限流、权限错误、参数错误和业务错误。瞬时错误采用指数退避和抖动；限流遵守服务端重试时间；参数错误可让模型在校验反馈下修复一次；权限和业务错误不盲目重试。可降级到备用工具、缓存结果或人工流程。产生副作用的调用要有幂等和补偿事务。

### 25. 如何避免 Agent 无限循环或反复调用同一工具？

设置最大步骤数、总时长、Token、费用和单工具调用次数；记录调用签名与结果哈希，检测重复；每一步必须产生可观察的状态进展，否则触发重新规划或终止。连续失败超过阈值时返回已完成内容、失败原因和建议，而不是继续消耗资源。

### 26. 工具调用成功但结果写回失败怎么办？

使用事务外盒或先记录调用请求与幂等键，再执行外部调用。写回失败后，恢复任务查询工具侧状态或根据外部事务号补写结果。对于无法查询的外部系统，调用结果应先写可靠消息或本地日志，再异步更新状态，避免把未知状态误判为失败并重复执行。

### 27. 如何给危险工具配置权限、审批和审计？

工具按读、写、资金、个人数据等风险分级；用户身份映射到细粒度权限；Agent 只获得任务期间的短期凭据；高风险操作展示目标、参数和影响并请求人工确认；执行后记录用户、模型、Prompt 版本、工具、参数摘要、结果和时间。敏感字段在日志中脱敏。

### 28. 错误参数应该由哪一层校验？

需要分层防御。模型层通过 Schema 尽量生成正确参数；编排层校验业务上下文、权限和调用策略；工具层必须做最终类型、范围、资源状态和权限校验，因为它不能信任调用方。越接近真实副作用，校验越严格。

## 三、简历项目深挖

### 29. 选择一个复杂任务，说明任务空间如何拆解和执行。

以“分析某汽车金融产品市场并生成汇报”为例：先澄清地区、时间和受众；规划为资料检索、来源筛选、竞品对比、数据计算、结论撰写、PPT 生成和质量检查；其中多个竞品调研可以并行，数据汇总完成后再生成观点；每个结论保留来源；最后检查事实一致性、版式和缺失信息，并输出 PPT 与引用清单。

### 30. 任务拆解是一次生成还是动态调整？

采用“初始计划 + 执行中调整”。开始时生成可解释的高层计划，执行过程中根据工具结果、失败和新信息修改未执行节点。已经完成且有副作用的步骤不能随意回滚；计划变化需要记录原因和版本，避免 Agent 无约束地不断改计划。

### 31. 如何衡量任务空间的成功率和结果质量？

分层评价：步骤层看工具成功率、重试率和状态接续率；任务层看完成率、人工接管率、耗时和成本；结果层看事实正确性、证据覆盖率、格式合规和用户评分；业务层看节省工时、复用率与最终采纳率。复杂任务不能只用一个“成功/失败”指标。

### 32. 如何确保调研报告引用真实？

搜索工具返回 URL、标题、发布时间和正文片段；每条事实保存证据 ID；生成阶段只允许引用证据库中的 ID；输出后进行引用存在性、内容支持度和时间有效性检查。无法找到可靠来源的结论要标为不确定，不能让模型补造链接。

### 33. 搜索结果相互矛盾时如何处理？

比较来源权威性、发布时间、统计口径和原始数据；优先监管机构、公司正式披露和原始研究；保留双方观点并解释差异，必要时继续检索第三方证据。系统不应强行给出唯一结论，而应输出置信度和需要人工判断的部分。

### 34. 自然语言如何转换成可执行 Skill？

先抽取目标、输入、输出、步骤、依赖、工具、权限和异常策略，转换成受控 DSL 或工作流 Schema；再进行静态校验和沙箱试运行；通过后生成版本化 Skill。LLM 负责理解和草拟，执行引擎只接受合法结构，避免直接执行自由文本。

### 35. Skill 的输入、输出、权限和依赖如何定义？

使用机器可读的 manifest：包含名称、版本、输入输出 JSON Schema、依赖工具及版本、超时、资源预算、权限范围、网络访问、敏感数据级别和错误码。这样可以在运行前校验兼容性，并支持审计和版本升级。

### 36. 如何防止用户生成的 Skill 包含恶意代码？

默认不允许任意代码执行；优先使用受控节点和白名单工具。确需代码时放入无特权沙箱，限制文件系统、网络、CPU、内存和执行时间；进行依赖扫描、静态检查和危险 API 检测；高风险权限必须人工审批；发布后保留签名和版本记录。

### 37. Skill 升级后如何保证已有工作流可运行？

采用语义化版本和不可变发布，旧工作流固定依赖版本；新增字段提供默认值，破坏性变更升级主版本；建立契约测试和回放测试；提供迁移脚本、灰度和回滚。不要让“最新版本”自动替换所有生产依赖。

### 38. Skill 复用和 Prompt 模板复用有什么区别？

Prompt 模板主要复用模型指令；Skill 是完整、可执行、可版本化的能力单元，包含输入输出契约、工具、流程、权限、异常处理和评测。Skill 可以包含多个 Prompt，也可以包含确定性代码和人工节点。

### 39. AI 手机卡片从用户意图到生成的完整链路是什么？

用户描述需求后，系统识别目标和所需应用能力；查询设备及应用能力目录；规划动作和卡片布局；进行参数、权限和安全校验；生成卡片定义并在预览环境验证；用户确认后发布到设备桌面。执行时还要记录实际调用结果，并在能力失效时提示或降级。

### 40. 为什么 AI 手机卡片需要设计网络拓扑？

它跨越手机端、云端 Agent、模型服务、能力网关和第三方应用。网络拓扑决定访问方向、鉴权位置、数据是否出域、故障隔离和发布方式。设计时需要明确端云协议、入口网关、服务发现、超时重试、网络分区和敏感数据传输边界。

### 41. 手机端、云端和第三方应用之间如何鉴权？

用户先在手机端完成身份认证，云端获取短期、范围受限的访问令牌；能力网关校验用户、设备、应用和具体操作权限；第三方应用使用 OAuth2/OIDC、签名请求或平台授权票据。令牌不写入 Prompt，不长期保存在 Agent 内存，高风险操作需要用户再次确认。

### 42. 如何处理不同应用能力、版本和权限差异？

建立带版本的能力注册表，描述应用、动作、参数 Schema、最低版本、权限和替代能力。规划前先做能力协商，执行前再次校验设备状态。能力不可用时选择兼容实现、引导升级或给出明确降级结果，不能让模型假设设备具备某项能力。

### 43. 卡片执行错误操作时如何追溯与恢复？

每次生成和执行都绑定请求 ID，记录用户意图、卡片版本、模型和 Prompt 版本、实际动作、参数摘要、授权和结果。可逆操作提供撤销或补偿；不可逆操作执行前必须预览和确认。发生问题时先禁用相关卡片版本，再依据审计链路定位是意图、规划、参数还是应用执行错误。

### 44. 深度搜索结果如何转化为 PPT 大纲？

先根据受众和目标定义故事线，再把资料归纳为主题、证据和结论，生成页级大纲，包括页面目的、标题、要点、图表建议和来源。大纲通过覆盖度、逻辑顺序和重复检查后，才进入内容与版式生成，避免边检索边排版导致结构混乱。

### 45. 如何避免内容与模板布局不匹配？

把模板解析成带容量约束的版式 Schema，例如标题长度、文本块数量、图表和图片占位。生成内容前选择合适布局，生成后计算文本溢出和元素冲突，必要时缩写、拆页或换布局。不能单纯依赖模型“猜”页面容量。

### 46. 如何评价自动生成 PPT 的质量？

从内容正确性、来源可靠性、结构连贯性、受众匹配、视觉可读性、模板一致性和可编辑性评价。自动指标可检查引用、重复、溢出、字号和对齐；最终还需要业务人员盲评。业务指标包括生成耗时、人工修改比例和最终采用率。

### 47. 生成 50 页 PPT 时如何控制一致性和上下文？

先生成全局大纲、术语表、视觉主题和事实库，再按章节分批生成；每章只加载相关证据和全局摘要；完成后运行跨页一致性检查，检测术语、数字、结论、重复和引用。用结构化状态代替把 50 页全文都塞入一个上下文窗口。

## 四、量化指标真实性追问

### 48. 吞吐量提升 40% 的基线是什么？

正确回答应明确基线，例如“优化前在相同模型、机器和请求分布下，每分钟完成 `[X]` 个任务；优化后为 `[Y]`，提升约 40%”。我的主要优化方向是任务并行编排和动态负载均衡。正式面试前必须补齐 `[测试环境、任务类型、X、Y]`，不能只说一个百分比。

### 49. 使用 QPS、并发任务数还是平均完成时间？

长时 Agent 任务不适合只看 QPS。我会以单位时间完成任务数作为主要吞吐量指标，同时报告端到端 P50/P95 时延、并发任务数、成功率和资源占用。若简历中的 40% 使用的是其他口径，应如实替换为实际口径。

### 50. 优化前后测试条件是否一致？

应保证模型版本、采样参数、机器规格、数据集、并发曲线和工具环境一致；采用预热后多轮测试，并报告波动区间。如果生产环境无法完全控制变量，应使用灰度流量或回放流量进行 A/B 对比，并说明结果属于工程观测而非严格实验。

### 51. 性能提升主要来自哪里？

根据简历可确认的主要来源是独立子任务并行化和动态负载均衡，减少串行等待和热点执行节点。是否还使用缓存、批处理或连接复用，需要按实际补充。建议回答时用性能剖析数据说明各优化项贡献，避免把全部提升归因于一个笼统的“架构优化”。

### 52. 92% 准确率对应多少测试样本？

简历没有样本数，面试时必须给真实数字：`[请按实际补充：样本数、类别数、时间范围]`。如果无法取得精确数字，应坦诚说这是项目验收口径，并说明自己负责的评测方法和已知局限，不要临场编造。

### 53. “客户认可”体现为什么？

应具体化为 PoC 验收、进入生产、业务使用、复购、用户评分或管理层评审通过。建议准备每个项目的真实证据：`[项目名称—当前阶段—用户/客户反馈—后续动作]`。如果只是演示获得积极反馈，应说“通过 PoC 评审”，不要说成商业收入。

### 54. 哪些项目是主导，哪些是参与？

建议明确 RACI：在 AI 手机卡片中负责网络拓扑、项目管理和交付发布；在多智能体平台中作为核心开发负责云侧算法与工程模块；任务空间、VibeSkill、小艺 Claw、AIPPT 的角色分别填写 `[主导/核心开发/参与，具体模块]`。回答重点是个人决策和交付，不要把团队成果全部归到个人。

## 五、LLM 与 RAG

### 55. 设计奔驰金融内部知识问答 RAG 系统。

我会设计文档接入、解析清洗、权限标注、切分、Embedding 与索引、查询理解、权限过滤、混合检索、重排、生成和引用校验链路。入口对接企业身份系统，文档级和片段级 ACL 贯穿索引与检索；回答必须附证据，证据不足时拒答。平台侧提供版本、评测、审计、监控和私有化模型网关。

### 56. 文档如何切分？

不是固定一种策略。制度和合同优先按标题、条款和语义边界切分，并保留章节路径；长段落再做带重叠的长度切分；表格作为整体或按逻辑行转换为结构化文本。通过检索评测选择块大小，目标是在上下文完整性和召回精度之间平衡。

### 57. Embedding 模型如何选择和评估？

先看语言、领域、上下文长度、部署方式、延迟和许可证，再用奔驰金融真实查询—相关文档标注集评估 Recall@K、MRR 和 nDCG。中文和中英混合场景要单独测试缩写、产品名和监管术语。最终选择不是看公开榜单最高，而是看领域效果、成本和私有部署能力。

### 58. 向量、关键词和混合检索的优缺点是什么？

向量检索擅长语义相似，但可能错过精确编号和专有名词；关键词检索对产品代码、法规条款和人名准确，但不理解同义表达；混合检索结合两者，通过分数融合或 Reciprocal Rank Fusion 提升稳健性。金融知识库通常适合混合检索再重排。

### 59. Recall、Precision@K、MRR 和 nDCG 是什么？

Recall@K 衡量前 K 个结果覆盖了多少相关文档；Precision@K 衡量前 K 个结果中相关结果的比例；MRR 关注第一个相关结果出现的位置；nDCG 同时考虑多个结果的相关等级和排序位置。RAG 更关注高召回与前排质量，还需要单独评价答案忠实度和引用支持度。

### 60. Reranker 放在哪里？成本是什么？

放在初步检索之后、上下文组装之前。先从大索引召回几十个候选，再用 cross-encoder 或 LLM reranker 选出少量高相关片段。代价是额外延迟和算力，因此需要控制候选数量、批处理、缓存，并对简单查询按需跳过。

### 61. 如何处理扫描件、表格、合同和多版本政策？

扫描件使用 OCR 并保存坐标和页码；表格采用结构化抽取并保留表头关系；合同按条款解析；政策文档记录生效、失效、地区和版本。查询时根据业务日期和适用范围过滤，只使用有效版本，并在回答中显示文档版本和页码。

### 62. 如何让回答只基于内部知识库？

Prompt 明确要求仅依据证据，但更重要的是系统层约束：只把检索片段提供给模型；要求每个关键结论绑定证据 ID；生成后运行蕴含或引用支持检查；证据不足则返回“不足以回答”。高风险场景可采用抽取式答案或规则模板。

### 63. 检索内容不足时如何拒答？

根据最高相关分、证据覆盖率和回答校验结果设阈值。低于阈值时说明未找到足够内部依据，列出已检索范围，建议用户补充条件、查看对应部门或提交知识缺口。拒答要可操作，不能只返回“我不知道”。

### 64. 如何实现部门级数据权限隔离？

文档入库时写入来源系统 ACL、部门、角色和敏感等级；查询时从身份令牌获取用户权限，并在检索层做服务端过滤。索引可按强隔离要求分库，也可使用元数据过滤，但不能只在生成后删除敏感内容。所有检索和下载行为进入审计日志。

### 65. 如何在不能联网的环境中部署？

采用本地模型服务、Embedding、reranker、向量数据库和对象存储；通过离线制品库管理镜像和依赖；模型与数据全链路不出域；使用内部 API 网关和身份系统；建立离线评测、资源容量和补丁升级流程。还要评估 GPU 可用性，用量化、批处理和缓存控制成本。

## 六、PoC 到生产：汽车金融智能信审助手

### 66. 两周内如何完成 PoC？

第 1–2 天与信审、合规和安全定义单一场景及成功指标；第 3–5 天准备脱敏样本、政策知识库和基线；第 6–9 天实现材料抽取、规则校验、RAG 证据和风险摘要；第 10–11 天离线评测和红队测试；第 12–14 天完成演示、业务验收和生产差距清单。PoC 只提供辅助建议，不自动审批。

### 67. PoC 最小功能范围是什么？

限定一种产品、少量材料类型和几个高价值风险点；输出结构化材料摘要、缺失项、政策依据、风险提示和待人工确认事项。暂不做全量系统集成、自动决策和复杂模型训练。成功标准是准确性、证据可追溯、节省审核时间和用户可接受性。

### 68. 哪些部分使用规则、ML、RAG 和 LLM？

硬性准入和金额阈值使用规则；历史数据上的违约概率可使用经过治理的传统 ML；政策、产品和流程知识使用 RAG；LLM 用于非结构化材料抽取、解释、归纳和交互。最终审批由现有决策系统和授权人员完成，LLM 不直接改变额度或批准结果。

### 69. 如何防止模型直接作出未经授权的信贷决策？

在产品、Prompt、接口和权限四层限制：界面明确“辅助建议”；模型输出 Schema 不包含最终批准动作；策略引擎阻断未经授权的写操作；所有建议需要人工确认；高风险字段和最终决策只能由授权系统写入。审计日志记录建议与最终人工决定的差异。

### 70. 如何设计人工审核流程？

AI 先提取事实、列出证据和风险项；审核员逐项确认、修改或驳回，并选择原因；低置信度和政策冲突自动升级；最终决定由有权限人员提交。人工反馈进入评测数据，但不能未经审核直接训练或更新生产模型。

### 71. 如何评估正确性、公平性和可解释性？

正确性看材料抽取准确率、风险点召回率、政策引用支持度和错误严重度；公平性按合法允许的群体切片比较误报、漏报和决策影响，并排查代理变量；可解释性要求每条建议展示输入事实、规则或政策证据。上线前由业务、模型风险、合规和法务共同评审。

### 72. 如何处理个人敏感信息？

遵循目的限定和数据最小化，只收集任务必需字段；传输和存储加密；日志脱敏；非生产环境使用脱敏或合成数据；权限按岗位和案件隔离；设置保留与删除周期。调用模型前确认部署区域和数据处理协议，禁止敏感信息进入未授权的外部模型。

### 73. 生产环境需要哪些服务？

包括接入/API 网关、身份权限、文档解析、规则服务、知识库与检索、模型网关、工作流编排、人工审核、案件与审计存储、监控告警、配置版本和 CI/CD。底层需要容器平台、密钥管理、对象存储、消息队列和灾备。

### 74. 如何管理模型、Prompt、知识库和规则版本？

每次请求绑定模型版本、参数、Prompt 版本、知识库快照、检索配置和规则版本。制品不可变并有审批记录；变更通过测试环境、离线评测和灰度；问题可以精确回滚到上一组合。审计时能够重放当时的输入和版本上下文。

### 75. 新版本如何评测、灰度和回滚？

先运行冻结数据集和安全回归，设置相对基线门槛；再以影子模式处理真实流量但不影响用户；通过后对小比例案件灰度，并监控质量、延迟、成本和人工修改率。配置和模型版本支持一键切回，数据库变更采用向后兼容设计。

### 76. 如何记录每次建议使用的模型、Prompt、规则和证据？

生成不可变审计记录：请求 ID、用户、案件、时间、输入摘要、模型与参数、Prompt 哈希、规则版本、检索查询、文档版本和片段 ID、工具调用、输出、人工修改和最终决定。敏感原文按权限独立存储，日志只保存引用和脱敏摘要。

### 77. 如何监控幻觉、延迟、Token 成本和业务采纳率？

幻觉通过无证据断言率、引用支持率和人工纠错分类监控；延迟按解析、检索、模型、工具分段统计 P50/P95；成本按模型、用例和案件聚合 Token/GPU；业务效果看建议采纳率、人工修改率、审核耗时和风险遗漏。指标异常触发降级或停用。

### 78. 完全私有化部署时如何调整？

选择可本地部署且许可证允许的模型，建立内网模型网关、GPU 资源池和离线制品库；所有文档、向量和日志留在受控域内；对模型做量化和容量规划；外部工具替换为内部服务；升级采用安全审核后的离线包。若本地模型能力不足，通过缩小任务、强化 RAG、规则和人工复核保证质量。

## 七、花旗金融系统经历（79–80）

### 79. 流动性风险管理平台解决什么核心问题？

它把全球流动性风险评估、质量审查、审批、问题跟踪和监管报告从分散的 Excel 与人工协作流程转为统一平台，解决版本不一致、过程不可追溯、效率低和数据安全风险。平台的核心价值是流程标准化、证据留存和多层级报告，而不是直接计算所有风险指标。

### 80. 风险评估、质量审查和审批流程如何建模？

以案件或评估任务为聚合根，包含模板版本、数据、状态、负责人和审计记录；流程使用状态机或工作流定义节点、角色、条件、退回和升级；每次提交产生不可变版本，审批意见与问题单独建模。权限同时考虑角色、地区、业务实体和任务归属。

### 81. 动态表格引擎的数据模型是怎样的？

可以分为模板和实例两层。模板包含版本、Sheet、行列、字段类型、公式、校验、权限和展示配置；实例保存模板版本、单元格值、计算结果和状态；公式使用字段 ID 而不是显示坐标，便于模板演进；变更和审批另存审计事件。大规模查询可增加宽表或报表快照，但源数据保持规范化。

### 82. 公式计算在前端还是后端？如何避免不一致？

前端可以即时计算以改善交互，但后端必须是权威结果。公式应有统一 DSL 和版本，前后端使用同一解析规范或共享计算核心；提交时后端重新校验并计算；关键结果保存公式版本、输入和输出。不能把监管相关计算只留在浏览器。

### 83. 动态表格如何支持版本、权限、审计和数据追踪？

模板发布后不可直接修改，通过新版本演进；实例固定引用模板版本；字段和操作按角色授权；每次修改记录操作者、时间、旧值、新值和原因；审批后数据进入只读状态，修订通过新版本完成。报表中的结果能够回溯到实例、单元格、公式和源数据。

### 84. 轻量工作流引擎包含哪些核心概念？

流程定义、版本、节点、连线、条件、任务、实例、变量、参与者、定时器、事件、状态迁移和审计。还需要幂等执行、失败重试、人工任务、退回、撤回和升级机制。轻量的含义是只实现业务需要的子集，而不是复制完整 BPM 产品。

### 85. 为什么自研而不是继续使用 JBPM？

需要结合真实背景回答：现有流程模式相对固定，而 JBPM 的采购、维护、升级和使用复杂度高；轻量引擎可以围绕实际节点、审批和审计需求降低依赖与成本。但自研必须评估长期维护、标准兼容和关键人员风险。只有需求边界清晰、团队具备维护能力时才合理。

### 86. 动态报表模块如何替代 MSTR？

将业务常用报表抽象为数据集、查询、维度、指标、过滤、权限、模板和导出任务；后端生成参数化查询或读取预聚合数据，异步生成 Excel/PDF 等产物。重点不是复制 MSTR 全部能力，而是覆盖高频固定场景，并提供权限、缓存、调度和审计。

### 87. 每年节省 50 万美元的依据是什么？

应拆成被替代的 MSTR/JBPM 许可证、维护合同、基础设施及必要支持成本，再扣除自研开发与持续维护成本。正式回答需补充 `[财务确认口径、涉及系统/许可证数量]`。如果 50 万是项目估算而非审计数字，要明确说“按采购和维护预算估算”。

### 88. 银行生产变更要经过哪些流程？

通常包括需求和风险评估、技术设计、代码审查、自动化测试、安全与开源扫描、UAT、变更单、职责分离审批、发布窗口、备份和回滚方案、生产验证及证据归档。紧急变更可以缩短流程，但仍需事后复盘和补充审批。具体以所在机构 SDLC 为准。

### 89. 如何处理生产故障并满足审计要求？

先控制影响：告警确认、分级、回滚或隔离；建立单一事件指挥和沟通渠道；所有操作通过授权账号和工单记录；修复后验证数据完整性；随后做根因分析、纠正措施和证据归档。不能为了抢修绕过权限，也不能在日志中写入敏感数据。

### 90. 花旗治理经验如何迁移到 GenAI？

把传统 SDLC 扩展为 AI 生命周期治理：代码版本之外，还管理模型、Prompt、知识库和评测集；变更前做质量、安全和偏差评测；生产中记录证据和人工反馈；高风险操作职责分离；供应商和开源模型进行许可证及安全评估。核心原则仍是可追溯、可审批、可回滚。

## 八、机器学习与论文

### 91. 为什么选择 nnU-Net？

nnU-Net 能根据数据自动配置预处理、网络、训练和后处理，是医学图像分割的强基线，适合数据规模有限且图像特性差异大的场景。选择它可以减少随意调参，并把研究重点放在针对眼眶淋巴瘤的特征和任务改进上。

### 92. 数据量多少？如何划分？

简历没有给出数量，必须填写真实数据：`[患者数、图像/切片数、类别数]`。划分应以患者为单位，而不是随机切图，采用训练、验证和独立测试集；样本少时可在训练集内部做交叉验证，但最终测试集保持冻结。

### 93. 如何避免同一患者进入训练集和测试集？

为每位患者建立不可逆的患者级 ID，以该 ID 进行 Group Split；同一患者的所有切片、增强样本和不同时间点数据必须在同一分区。划分后运行重复和元数据校验，防止文件重命名导致泄漏。

### 94. 图像分割使用哪些指标？

主要使用 Dice 和 IoU 衡量区域重叠，可补充 Precision、Recall、Hausdorff Distance 观察边界和漏分割。医学场景还要按病灶大小、设备或亚型切片分析，不能只报告总体平均值。实际论文使用的指标请按真实内容替换。

### 95. 分类准确率 87% 是否足够？

不能只凭准确率判断。需要看类别分布、敏感度、特异度、AUC、置信区间和与医生/基线的比较。若用于临床辅助，尤其要关注高风险类别漏诊，并开展外部验证。87% 可以证明研究可行性，但不等于能够直接临床部署。

### 96. 为什么选择 XGBoost 而不是端到端深度模型？

在样本有限、特征具有明确医学意义时，XGBoost 对结构化空间和纹理特征稳健、可解释、训练成本低，也便于分析特征贡献。端到端模型可能获得更高上限，但更依赖大规模数据和严格正则化。最好通过统一划分的对照实验选择。

### 97. 空间和纹理特征包括什么？

空间特征可包括病灶位置、面积、体积、形状、长短轴、边界和左右侧关系；纹理可包括灰度共生矩阵、局部二值模式、一阶统计和小波特征。正式回答只列论文中实际使用的特征，并说明标准化和特征选择方式。

### 98. 如何处理类别不平衡？

患者级分层划分；使用类别权重、适度过采样或针对少数类的数据增强；阈值按业务代价调整；评价使用宏平均 F1、每类 Recall、PR-AUC 和混淆矩阵。不能先在全量数据上过采样再划分，否则会造成数据泄漏。

### 99. 两篇论文中你的具体贡献是什么？

建议按 CRediT 口径准备：问题定义、数据整理、方法设计、代码与实验、结果分析、论文写作分别承担什么。可回答：“我负责 `[请按实际补充]`，共同作者负责 `[请按实际补充]`。”同时能解释论文核心图表和消融实验，证明不是只参与署名。

### 100. 如果重新开展项目，会如何改进？

扩大多中心数据并保留外部测试集；统一标注协议并测量标注者一致性；增加端到端模型和自监督预训练基线；报告置信区间和分层指标；加入模型校准、可解释性和临床工作流评估；从实验开始就建立数据与模型版本管理。

## 九、软件工程与生产能力

### 101. Python 和 Java 分别适合哪些模块？

Python 适合模型推理、数据处理、Prompt/Agent 快速迭代和 ML 生态集成；Java 适合强类型、复杂事务、高并发和成熟治理的企业核心服务。实际架构可让 Python 承担 AI 能力服务，Java 承担业务编排、权限和交易系统，通过稳定 API 或消息协议协作。

### 102. 如何设计可扩展模型网关？

提供统一 Chat/Embedding/Rerank 接口，使用适配器接入云端和本地模型；支持路由、鉴权、配额、限流、超时、重试、熔断、流式响应、缓存和内容安全；记录模型版本、Token、延迟和成本；策略层可按任务、数据级别、质量和价格选模型，并支持灰度与回退。

### 103. LLM 请求如何限流、超时、重试和熔断？

按用户、应用和模型设置令牌桶；连接、首 Token 和总请求分别设置超时；仅对网络错误、限流等可恢复错误重试，并采用指数退避；达到失败阈值后熔断，转备用模型或降级。流式请求中断需要明确是否允许从头重试，避免重复计费和重复副作用。

### 104. 如何保证消息任务不丢、不重复？

生产者使用事务外盒或发送确认；Broker 开启持久化和副本；消费者在业务事务成功后再确认消息；通过业务唯一键和去重表实现幂等。严格的“恰好一次”通常由至少一次投递加业务幂等实现，不能只依赖消息队列宣传语。

### 105. Redis 在 Agent 系统中能做什么？

可用于短期会话、任务状态缓存、分布式锁、限流、幂等键、能力注册和热点结果缓存。Redis 不应成为唯一的长期任务事实源；重要状态需落持久数据库。锁要设置租约和所有者校验，避免误删他人锁。

### 106. Kubernetes 中如何为 Agent 服务扩缩容？

无状态 API 可按并发、队列长度、P95 延迟或自定义任务指标 HPA；长时 Worker 按待处理任务和预计工作量扩缩；GPU 推理服务需要节点池、模型预热和较慢的缩容策略。任务状态外置，Pod 终止前停止接新任务并保存检查点。

### 107. 为什么不能只按 CPU 扩缩大模型服务？

瓶颈通常在 GPU 显存、KV Cache、并发序列、输入输出 Token 和队列，而 CPU 可能很低。应观察 GPU 利用率和显存、排队长度、首 Token 时间、生成速度、批大小和请求长度，并结合模型加载时间做预测性扩容。

### 108. 如何设计日志、指标和链路追踪？

使用统一 Trace ID 串联入口、规划、模型、检索和工具；日志记录结构化事件并脱敏；指标覆盖流量、错误、延迟、饱和度以及 Token、成本、工具成功率和任务完成率；Trace 记录每个 Span 的耗时和版本。对于模型内容只按授权保存摘要或哈希。

### 109. 如何管理 API Key 和模型凭据？

存入企业密钥管理系统，通过工作负载身份或短期令牌动态获取；禁止写入代码、镜像、Prompt 和普通日志；按服务和环境隔离权限；定期轮换并监控异常使用。CI/CD 只传递引用，不在构建输出中暴露明文。

### 110. Sonar、Black Duck 和 AppDynamics 分别解决什么问题？

Sonar 主要进行代码质量和静态缺陷分析；Black Duck 用于开源组件识别、许可证和已知漏洞治理；AppDynamics 侧重运行时应用性能监控和链路诊断。三者分别覆盖源代码、供应链和生产运行，不能相互替代。

## 十、行为与技术领导力

### 111. 描述一次 PoC 未达到预期的经历。

不要虚构失败项目。建议选择真实案例并用 STAR 回答：“目标是 `[目标]`，早期假设是 `[假设]`；验证发现 `[质量/数据/集成]` 不达标；我通过缩小范围、增加评测和与业务确认，决定 `[调整/停止]`；最终避免了 `[损失]`。复盘后把成功指标和退出条件前置。”若没有完整失败，可讲一次方向调整，但要诚实。

### 112. 业务要快速上线，安全团队不同意怎么办？

先把争议从立场转为具体风险和控制项，确认阻断原因；提供分级方案，例如脱敏数据、只读工具、内网部署、人工审批、限定用户和时间的沙箱试点；记录风险接受人和退出条件。不能绕过安全上线，也不能只说“不行”，应给可验证的最小安全路径。

### 113. 产品经理提出无法量化价值的 AI 需求怎么办？

追问目标用户、当前流程、痛点频率和不用 AI 的基线；将价值拆为节省时间、质量、转化、风险和体验；定义两周 PoC 与停止条件；先做人工或规则基线。如果连用户和决策都无法说明，就不进入重投入开发。

### 114. 如何向非技术管理者解释 LLM 幻觉？

我会说：模型更像一个擅长组织语言、但有时会把不确定内容说得很肯定的助手。解决方式不是要求它“永不犯错”，而是给它可信资料、要求出示依据、限制能执行的动作，并让高风险结果经过人工复核。随后用本业务的错误率和风险示例说明，而不是只讲术语。

### 115. 描述一次技术意见不一致。

建议用真实案例，例如自研轻量工作流与继续使用 JBPM 的取舍。回答结构：双方目标一致但关注点不同；列出需求覆盖、成本、维护和风险数据；做小型原型或决策记录；邀请相关方评审；决策后共同执行，并说明最终结果和复盘。避免把对方描述为不专业。

### 116. 如何推动跨部门项目从演示走向生产？

演示后立即形成生产差距清单：业务负责人、数据、合规、安全、架构、SLA、评测、运维和成本；明确 RACI 和里程碑；将原型重构为版本化服务；建立冻结评测集和上线门槛；先灰度给小用户群；用业务指标决定扩展，而不是以演示效果决定上线。

### 117. 多个 AI PoC 如何排序？

按业务价值、可行性、风险、数据准备度、复用价值和交付周期评分。优先高价值、低风险、数据可得且能沉淀公共能力的项目；监管高风险但价值大的项目先做受控研究。还要限制并行数量，确保每个 PoC 有业务 Owner 和明确退出条件。

### 118. 如何建立 Prompt、评测和 Agent 开发规范？

Prompt 使用模板、变量 Schema、Owner、版本和变更记录；评测集覆盖正常、边界、安全和回归场景，版本冻结；Agent 工具必须有输入输出契约、权限、幂等和超时；上线要求代码审查、离线评测、红队、灰度和回滚；所有调用记录模型、Prompt、工具和成本。

### 119. 过去一年研究了哪些 AI 技术？如何判断是否采用？

可结合真实经历回答 MCP、A2A、多智能体、Subagent、Skill/Channel 和长时任务。判断采用时看是否解决明确痛点、相对基线的质量提升、延迟成本、生态成熟度、安全、私有部署和迁移成本；先用小基准和受控 PoC 验证，不因热度直接进入生产。

### 120. 入职 90 天计划是什么？

前 30 天理解业务、数据、系统和治理流程，访谈信审、客服、运营、合规和 IT，建立用例清单与技术现状图；31–60 天选择一个高价值低风险场景完成可量化 PoC，同时设计评测和安全基线；61–90 天推动受控试点，并沉淀模型网关、RAG、Agent 工具契约、Prompt 版本和监控等可复用基础能力。
